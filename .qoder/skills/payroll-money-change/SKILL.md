# 金额与政策口径改造

## 适用场景

- 改 `PayrollEngine`、`Money`、`PayrollPolicy`、城市政策、个税/社保逻辑；
- 调整应发/实发/企业成本的计算项，或新增一种扣款、津贴、奖金；
- 排查「同一员工同一月份两个金额」「审批后出账 409」「Excel 与对话答的对不上」。

## 铁律

1. **金额只有一个出口**：`PayrollEngine`。任何在 Controller、Excel、工具、提示词里做的二次计算都是错的。
2. 全链路 `BigDecimal`；舍入只走 `Money.round`（SCALE=2，HALF_UP）；中间精度（日薪/时薪）用 `Money.divide(..., 10)` 再收敛。禁止 `double`、禁止手写 `setScale`。
3. **累计预扣的「累计已预扣」是既成事实**，不能由重算推导；没有 withholding 记录时先补数据，不要改算法绕过。
4. 政策是「某城市 + 某社保年度」的口径，按**工资期间**取，不按"当前时间"取。

## 步骤

### 1. 先复现，再动手

写一条当前会失败的单测（放 `payroll-tests` 对应子包），断言具体金额字符串：

```java
assertEquals("12345.67", result.netPay().toPlainString());
```

复现不出来说明还没定位到根因，不要开始改。

### 2. 定位口径链

依次确认四件事，每件都要能指到文件：

- 取哪份政策（城市是否存在、是否按期间取版本）；
- 累计状态从哪来（内存重放 / 落库）；
- 哪些项进应发、哪些进扣除、企业成本怎么算；
- 舍入发生在哪一步（月、日、小时各自一次还是只最终一次）。

### 3. 改引擎，不改调用方

先改 `PayrollEngine` 与 `PayrollPolicy`，让调用方零改动即生效。需要改调用方签名时，说明为什么不能保持兼容。

### 4. 影响面闭合（最容易漏）

| 影响面 | 检查点 |
| --- | --- |
| 工具输出 | `PayrollTools` 返回的字段与金额是否仍自洽（模型据此作答） |
| Excel | `ExcelExporter` 的列与合计是否同步 |
| 审批指纹 | `ApprovalService.snapshotHash` 覆盖的 JSON 变了 → 在途批次会 409 |
| 预览/出账 | `PayrollRunService` 预览与 `finalize` 重算必须同口径 |
| 前端 | 页面展示位、千分位格式、负数 |
| 测试 | 金额断言、边界（0、负数、封顶、未入职） |

### 5. 历史数据处理

- 只影响未来月份 → 不迁移，在发布说明写清生效期间。
- 影响已出账月份 → 提供回填作业 + dry-run 计数 + 回填前快照，并明确「已出账只读」。
- 涉及新表/新列 → 按 `payroll-db-migration` 技能走。

## 验收

- [ ] 复现用例从红转绿，且把修复删掉会变红。
- [ ] 给出「同员工同期间，修复前后金额对比」的记录。
- [ ] 全量 `mvn -o test` 绿（金额逻辑属共享逻辑）。
- [ ] 真实跑一轮对话，`calculate_payroll` 工具结果与页面/Excel 三处一致。

## 反例

- 在提示词里写「税额四舍五入」来解决精度问题——模型不算钱，改提示词不改变数值。
- 用 `Math.round` 或 `double` 做中间计算再转 `BigDecimal`。
- 为了让在途批次能出账，去改指纹算法——应该重新提交审批。
