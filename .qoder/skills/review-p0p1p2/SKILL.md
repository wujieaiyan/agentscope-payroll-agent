# P0/P1/P2 评审

## 分级定义

| 级别 | 判定 | 例子 |
| --- | --- | --- |
| P0 | 会导致数据错误/丢失、越权、密钥泄露、生产不可用，或功能主路径不可用 | 缺权限校验；事务边界错误导致重复扣减；凭据写进日志或仓库；迁移脚本与实体不一致 |
| P1 | 明显缺陷或高风险设计，边界条件下会出错，或显著增加维护成本 | 异常按消息文本分支；并发下会话状态竞争；N+1 查询；错误被吞掉只打 debug |
| P2 | 可维护性、一致性、体验细节，不影响正确性 | 命名不一致；缺空态；文档缺口；测试覆盖不足 |

不确定级别时按影响面判断：**能否在正常使用中触发** → 能且后果重则 P0，能但后果轻或需特定条件则 P1，否则 P2。

## 输出格式

```
结论：不建议合并 / 可合并但需先修 P0 / 可合并
范围：本次评审覆盖的文件与提交

P0
1. <问题一句话>
   证据：path/File.java:123
   影响：...
   修复：...

P1
...

P2
...
```

## 评审方法

1. **先读全量改动的 diff**，再看被改函数的调用方与依赖方，避免只看片段下结论。
2. 每条结论必须能指到具体行；指不到就标「待确认」并说明缺什么信息，不要凭印象断言。
3. 检查清单：
   - 权限：新接口是否登记权限码并加注解；越权路径是否可达。
   - 数据：H2 建表与 MySQL 迁移是否同步；事务边界；幂等。
   - 安全：密钥/口令是否可能进入日志、异常消息、前端包；SQL 拼接；内部接口签名与时间窗。
   - 并发：会话锁、fencing、异步写库的失败处理。
   - 异常：是否按类型分支；是否吞异常；用户可见错误是否清晰。
   - 测试：主路径与边界是否有测试；测试是否依赖真实外部服务。
   - 前端：构建通过、空态/加载态/错误态、权限菜单可见性。
4. 不要为了凑数报 P2；没有问题就说没有。

## 复审

用户说「已修」后：

- 逐条回读对应文件与行号，确认修复真实存在且没有引入新问题。
- 已修复标「已修（证据）」，未修或修错标「未修（原因）」，新发现单列。
- 汇总前后数量变化：P0 x→y，P1 x→y，P2 x→y。
