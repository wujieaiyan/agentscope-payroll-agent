# 规格可实施性审计

## 适用场景

- 规格已评审 1–2 轮，准备排期或开工。
- 用户问「这个方案能不能直接照着写」「是否具有可实施性」「再审视一遍」。
- 改动跨模块、涉及迁移、容器卷、配置键或上下文语义。

与 `spec-first`、`review-p0p1p2` 的分工：`spec-first` 产出规格；`review-p0p1p2` 评审代码；本技能只回答一个问题——**一个不了解背景的工程师照这份规格写，能否一次写对**。

## 为什么两轮复审仍会漏

复审失效通常不是不够仔细，而是**看错了对象**：

1. 审的是文档内部一致性，没有逐条回读代码。
2. 只看「设计有没有写」，没做「照着写会编译失败吗」的模拟。
3. 规格点名的类型/方法/配置键没有逐一解析是否存在。
4. 迁移只算了主代码调用方，漏掉公有静态、嵌套类型、测试与 pom。
5. 容器路径只在文字层校验，没代入只读卷与实际挂载点。
6. 第二轮沿用第一轮的视角与结论，变成确认而非重推。
7. 验收标准不可证伪，P0 没有一条「今天就会失败」的用例。

以下流程逐条对治。缺任何一步，都不能给出「可实施」的结论。

## 审计流程

### 0. 主张清单（先建账，再判断）

通读规格，把每个可验证断言抽成一行，禁止凭印象评审。

| 编号 | 主张（原文摘要） | 类型 | 解析目标 | 结论 |
| --- | --- | --- | --- | --- |
| K1 | 摘要按轮次截断安全 | 数据语义 | `ConversationContext.java`、读取窗口 | 不成立 |
| K2 | 端口支持窗口读取 | API | `ChatContextStore` | 方法不存在 |

类型只用七种：证据、API、配置、迁移、路径、测试、回滚。
结论只用三种：成立 / 不成立 / **未验证（原因）**。禁止「应该可以」。

### 1. 字面实现模拟

对方案里的每个改动点，打开目标文件，按规格原文写出**将要产生的 diff**，然后自问：

- 编译能过吗？方法签名、可见性、泛型、import 是否齐全。
- 被调用的方法现在存在吗？不存在时，规格有没有把它列入「新增」清单。
- 构造函数/装配会多出哪些参数？Spring 能否解析。
- 状态字段的读写方是否都改了（只改写方是最常见的半成品）。

模拟不出来的地方，就是规格的空白，直接记为 P1。

### 2. 影响面闭合

对每个「新增/迁移/改名/下沉」的实体，机械地跑一遍：

- `grep` 全部引用（含 main、test、resources、frontend、docker、docs 示例）。
- 公有静态常量、嵌套类型、枚举、序列化字段是否随之移动。
- 测试模块 pom 是否需要新增依赖；测试源码的 import 是否要改。
- ArchUnit/包边界规则是否会因新命名空间而失败或失效。
- 旧路径是否保留一个版本；删除项是否登记里程碑。

只统计「主代码调用方」的影响面一律视为未闭合。

### 3. 环境组合

把规格里的每个路径、端口、卷、环境变量代入真实部署拓扑：

- 配置键：代码 `@Value` 的键名与 yml 是否逐字一致；默认值是否一致；是否与既有键重叠且默认值冲突。
- 卷：同一路径在哪些服务上出现、读写权限分别是什么；只读卷下写文件会在哪一行失败。
- 产物/上传/输出目录是否互相嵌套；只读父目录会连带锁死子目录。
- 端口、内网地址、健康检查路径是否与 compose/Dockerfile/nginx 对得上。

文字上「已隔离」不算数，要落到具体挂载点与权限。

### 4. 数据语义

对每个跨层状态变量追问：**它的定义在读写两端是否仍是同一个意思**。

- 绝对值还是相对值（累计轮次 vs 窗口内轮次）。
- 单位（条/轮/页/字节/毫秒）。
- 排序键与去重键（`message_id` vs `started_at` vs `seq`）。
- 截断点：谁截、截多少、截断后另一个使用方还能否正确解释。
- 迁移后的历史数据由谁补齐，补齐前读路径是否安全。

这一层最容易被「机制存在」掩盖——摘要、水位、租约都存在，但语义已错位。

### 5. 验收可证伪

每个 P0/P1 必须能写出**当前代码会失败**的用例：

- 现象级：给定输入，断言具体输出（第 4 轮仍在上下文里）。
- 环境级：给定挂载/配置，断言具体失败（对只读卷写文件返回拒绝）。
- 兼容级：旧客户端不带新参数，断言行为不变。

写不出失败用例的验收项，等价于没有验收；补用例或降级该主张。

### 6. 第二轮独立复审

第二轮不是把第一轮再看一遍：

- **换角色**：第一轮架构视角，第二轮实现/运维视角（编译、挂载、迁移、回滚）。
- **换起点**：从目标代码与 `git diff` 重新推导风险，不先读第一轮结论。
- **后比对**：两轮清单都产出后再 diff。新增项说明第一轮视角有盲区；重复项才是稳定结论。
- 至少抽 3 个第一轮判「成立」的条目重新证伪，而不是只复核「不成立」项。

## 本项目检查表

- Maven：根 `pom.xml` 是否注册新模块；`payroll-tests/pom.xml` 是否加依赖；包名是否落在 ArchUnit 允许的命名空间。
- Spring：新 Bean 是否声明；端口与实现是否分离；`@Value` 键是否在 yml；`@Profile` 是否让非生产环境无法演练。
- 数据库：迁移是否在 `payroll-common/src/main/resources/db/migration/common/`；H2 `MODE=MySQL` 与 MySQL 是否都能跑；列名/主键是否对得上既有 V1–Vn；DDL 非事务的补跑策略。
- Compose：卷路径、只读/读写、是否所有相关服务都挂载、`healthcheck`、`mem_limit`、端口。
- 配置：新增键是否进入配置清单；默认值与代码默认值一致；不与既有键同义不同名。
- 前端：后端能力是否有可见入口；新参数是否向后兼容。
- 测试：单测、集成、全量回归，以及 nginx 真实页面与 runtime 真实对话。

## 输出格式

```markdown
## 结论
可实施 / 有条件可实施 / 不可实施（一句话，附条件）

## P0（数据丢失、越权、生产不可用）
- [标题] 证据 file:line；照规格实现的具体后果；修法

## P1（按规格写会返工或半成品）
- 同上

## P2（一致性、可观测性、文案）
- 同上

## 未验证
- 项 + 原因 + 需要的环境/数据
```

每条必须能指到 `文件:行号` 或明确指出「该类型/键当前不存在」。不引用聊天记录里的密码、令牌与私钥。

## 收尾自检

- [ ] 每条主张都有结论，没有「应该」「大概」。
- [ ] 规格点名的每个类型、方法、配置键、路径都已解析或明确标为新建。
- [ ] 每个 P0/P1 都有可证伪的验收用例。
- [ ] 第二轮是从代码重推，并 diff 过两轮清单。
- [ ] 未验证项已单列，未混入「成立」。

## 脚本

`scripts/check-spec-claims.sh <spec.md>` 做机械核对：

- `文件:行号` 引用能否解析（支持裸文件名、`.../` 缩写、多行范围），行号是否越界；
- 反引号里的 Java 类型能否在仓库找到，找不到的列为「新建或外链，需人工确认」；
- 规格引用的 `payroll.*` 配置键是否已登记在 §6 清单，或已存在于代码。

脚本只做账本，不替人下结论；退出码非 0 表示存在硬失败（引用不可解析、键既未登记也不存在）。
