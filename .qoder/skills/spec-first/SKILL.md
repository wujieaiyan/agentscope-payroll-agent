# 规格先行

## 适用场景

- 新功能跨 2 个以上模块，或涉及数据库结构、权限、外部依赖。
- 用户说「出方案」「先设计」「写个规格」「这个需求怎么做」。
- 存在多方案取舍，直接编码会产生返工。

## 步骤

### 1. 收集事实，不臆测

读现有代码与配置，确认：模块边界、已有同类实现、表结构与迁移文件、权限码、配置项、前端路由。规格里每个「现状」都要能指到文件。

### 2. 写规格文档

建议放 `docs/`，按现有文档风格命名。结构：

```markdown
# <功能> 规格 v0.x

## 1. 背景与目标
## 2. 范围（做什么 / 不做什么）
## 3. 现状
## 4. 方案设计
  4.1 数据模型
  4.2 后端接口
  4.3 前端
  4.4 权限
## 5. 决策点 D1..Dn
## 6. 分期（P0 / P1 / P2）
## 7. 验证方式
## 8. 风险
```

### 3. 决策点显式编号

每个决策点写：问题、候选方案、推荐项与理由、影响面。**没有确认的决策点不进入实现。** 一次最多抛 3–4 个决策点，避免审讯式提问。

### 4. 确认即回写

用户确认某项后，立即把它写回规格正文所有相关段落（数据模型、接口、前端、验证），不要只在决策点列表里打勾。规格内部不允许出现互相矛盾的旧描述。

### 5. 分期实现

- P0：最小可用闭环，含落库与权限。
- P1：体验与完整性（筛选、空态、错误处理、测试补全）。
- P2：优化（性能、图表增强、文档）。
- 每期完成后更新规格状态，再进入下一期。

## 输出纪律

- 规格是给实现者看的：字段名、接口路径、权限码、表名要具体。
- 不写「后续可考虑」这种无 owner 的悬空项；要么进 P2，要么删掉。
- 实现阶段发现规格有误，先改规格再改代码，并在汇报里说明改了什么。
